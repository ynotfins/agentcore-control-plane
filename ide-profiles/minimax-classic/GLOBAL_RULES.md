## Mandatory rules

1. **AgentCore authority.** D:\github\agentcore-control-plane is the single source authority. Read order: PROJECT_ANCHOR.md -> DOC_AUTHORITY.md -> BLUEPRINT.md -> CONTEXT_BLOCK.md -> docs/memory-platform/MEMORY_PLATFORM_EXECUTION_PLAN.md -> Bifrost contracts/handoff -> D:\ChaosCentral-Current-Build\DOC_AUTHORITY.md (machine facts). D:\MCP-Control-Plane is evidence only.
2. **One Bifrost gateway entry plus Zoo-Code exception.** Non-Swarm IDEs use exactly one AgentCore MCP entry: agentcore-gateway at `http://127.0.0.1:8080/mcp` with Authorization Bearer ${env:BIFROST_MCP_VIRTUAL_KEY}. Operator approval AUTH-2026-08-20-ZOO_CODE_DIRECT_MCP_EXCEPTION allows one additional Zoo-Code-owned direct MCP companion entry where the host supports Zoo-Code and the operator wants the Zoo-Code side-panel workflow. That companion is not an AgentCore memory route, not a Bifrost replacement, and not permission to add any other direct MCP baseline. Never paste the upstream registry or direct per-tool MCP entries into IDE configs.
3. **CLIENT-LOCAL EXECUTION SCOPE.** The IDE running this prompt may inspect and modify only its own live configuration, rules, agent settings, and backup. Configuration examples for other IDEs are reference material only. Do not inspect, back up, repair, restart, validate, or modify another IDE. Cross-IDE reconciliation is a separate AgentCore control-plane task that requires explicit operator authorization.
4. **Swarm isolation.** SwarmVault and SwarmClaw are a separate execution ecosystem. Neutral shared SwarmRecall is the PC-native semantic memory/context plane and may be used by AgentCore only through the server-side agentcore-memory access facade/projection adapter; ordinary IDEs must never receive raw SwarmRecall MCP tools, database credentials, or Recall API keys. Never require SwarmVault, SwarmClaw, or Swarm-owned file roots for AgentCore / enrolled non-Swarm work. Never modify Swarm product installs. OpenClaw/ClawX are Swarm-managed and outside the AgentCore baseline. AgentCore PG18 remains canonical for exact evidence, recovery, policy, generated projections, and LangGraph checkpoints. No normal AgentCore IDE continuity on Swarm projects: if the selected path is Swarm-owned, HARD STOP with swarm_project_refused. Do not persist Swarm work through AgentCore memory, project router, or IDE profiles. A neutral dual workspace may be used only for read-only collision and boundary audits. SwarmClaw uses its own Recall adapter and native application databases; shared Recall does not merge execution authority.
5. **New Project Bootstrap (Milestone 0).** Every new managed project runs Milestone 0 per docs/agent-policy/NEW_PROJECT_BOOTSTRAP.md before broad implementation: register worktree, load context, preserve the operator prompt verbatim, run repo-local Context Fabric capture/drift, discover architecture with native project tools and explicit-cwd diagnostics, resolve exact versions via Arabold, create governance files from templates, audit tools.
6. **Concurrent-safe project-local toolchain.** For every nontrivial implementation, debugging, refactor, architecture, or recovery task, resolve the exact workspace through the IDE/workflow host and follow the wiring/runbook in D:\github\agentcore-control-plane\SERENA.md. Use native project-scoped semantic/source tools by default. Serena may run only as an explicit project-owned local process; Depwire and Tentra use explicit-cwd local diagnostics; Context Fabric uses its repository-local hook/CLI. Their implicit-project shared Bifrost clients remain dormant until trustworthy per-session project identity is carried on every call. Use sequential-thinking for planning and critique, arabold-docs for exact-version external documentation, and Artiforge for high-leverage architecture scans. Do not use machine-global project-router activation as an IDE continuity or concurrency boundary. Swarm runtime remains outside AgentCore and must be refused with swarm_project_refused.
7. **Effectively-unbounded durable memory.** AgentCore durable project memory is effectively unbounded by model-token limits. Preserve accepted raw prompts, visible responses, evidence, decisions, tool/test results, state transitions, Git references, summaries, source edges, and artifact locations with provenance. Model context limits control only one assembled request. Compaction is non-destructive: summaries are versioned and expandable, and no summary may replace or delete canonical originals. Preserve the operator prompt verbatim after secret redaction; never store hidden chain-of-thought or private reasoning.
8. **Canonical memory recovery before operator repetition.** Never assume information is permanently lost because it is absent from the current chat. Before asking the operator to repeat project history, query agentcore-memory. Use retrieve_context for bounded chronology and stable pagination, expand_source for exact original verification, and build_handoff for current project reconstruction. If model compaction appears wrong, rebuild context from PostgreSQL and retained artifacts instead of trusting the compacted chat. Never directly edit GLOBAL_STATE.md or project STATE.md; they and COMB files are concise generated projections. Record recovery and summary-correction events, and exclude quarantined evidence from normal startup context.
9. **Continuous durable capture and project-centric resume.** Project memory is project-centric, not IDE-folder-centric. Canonical project history lives in PostgreSQL and generated projections (`{project}\.agentcore\STATE.md`, DECISIONS.md, CONTEXT_INDEX.md). Client-specific directories under `F:\AgentCore\runtime\clients\{client_key}\` may hold only cache, logs, scratch, and temporary bundles — never canonical project history. At every new IDE chat or process restart: (1) resolve the exact project/worktree through the host and pass its explicit identity to memory calls without changing machine-global router state; (2) read generated STATE.md; (3) open or resume the correct session using a stable session_key — reuse the same session_key when continuing the same task, create a new session_key for a new task under the same project; (4) call startup_context with the selected model profile; (5) use retrieve_context for missing chronology; (6) use expand_source for exact original verification; (7) verify project, repository, worktree, client, agent, session, and thread identity before proceeding. Before tool execution, append the original visible operator prompt verbatim (after secret redaction) using a deterministic idempotency key bound to project/client/agent/session/run. During work, append accepted requirements, constraints, decisions, blockers, tool results, test results, commits, state transitions, and recovery events as they become durable — after each completed meaningful Micro step, not only at session_close. At clean task or session close: append final verified state, queue or complete compaction, regenerate STATE/DECISIONS/CONTEXT_INDEX, build the deterministic handoff, call session_close. On restart after an unclean exit: locate the latest open session for the same project/client/task, resume it safely, retrieve events after the last projection, rebuild startup context, and record a recovery event. Cursor Stage B integrity harness (2026-07-24): project hooks (sessionStart, beforeSubmitPrompt, preToolUse, beforeShellExecution, afterFileEdit, postToolUse, stop) registered via scripts/agentcore_cursor/hook_dispatcher.py; Continue. hard gate and 26/26 acceptance suite PASS (audits/cursor-context/CURSOR_STAGE_B_INTEGRITY_HARNESS_ACCEPTANCE_2026-07-24.md). Hooks fail open on internal errors and never emit followup_message or continual-learning prompts. Runbook: docs/operations/AUTOMATIC_NEW_CHAT_RECOVERY.md. An IDE is not live_validated if it can see tools but does not complete the full memory lifecycle: session_open → startup_context → append_event → retrieve_context → expand_source → build_handoff → session_close. Do not lower the IDE model's configured hard context limit. Never create a separate canonical database, schema, or project-memory copy per IDE client.
10. **Milestone execution.** Work is organized in Milestones (outcome boundaries) with entry and exit gates per docs/agent-policy/MILESTONE_EXECUTION_STANDARD.md. A Milestone is not complete until its exit gate passes, including validation runs and checkpoint evidence.
11. **Macro and Micro steps.** Macro steps are workstreams with Micro checklists. Micro steps are atomic and independently verifiable, with expected output, validation, and evidence location.
12. **Evidence-backed checklists.** Checklist state is machine-readable (status vocabulary: pending, in_progress, passed, blocked, failed, skipped_with_reason). passed requires an evidence reference. Markdown checkboxes are generated projections, never the canonical state. No step is complete from intention, confidence, or narrative claims.
13. **Dedicated documentation guard and maintainer.** Ordinary agents and implementation workers do not directly edit documentation. They submit a bounded proposed change and evidence to the read-only documentation guard. Only the AgentCore documentation maintainer may apply an existing-file documentation change, and it must internally obtain ACCEPT for the actual proposed diff rather than trusting a caller verdict. Protected documents still require live authority-maintainer capability, matching explicit AUTH approval, external rollback, validators, and independent review. Generated STATE.md, DECISIONS.md, CONTEXT_INDEX.md, and global-state projections remain projection-worker-only. An IDE without the Codex-owned workers must hand off the proposal; never install a second worker MCP entry or expose it through Bifrost merely to bypass this rule. Authority and procedure: docs/agent-policy/DOCUMENTATION_GOVERNANCE.md.

Projects begin with the Bootstrap profile, never unrestricted administrative or destructive authority. Do not ask permission for these routine post-task commits. Narrowest relevant validation plus secret/junk scan first; stage only source-controlled files; concise commit message. Never pull/fetch/merge/rebase or force-push without explicit operator instruction. See docs/GIT_PUSH_ONLY_POLICY.md.
